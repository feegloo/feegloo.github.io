1. Co przygotowujemy i dlaczego

Zainstalujesz aplikację na zarejestrowanym iPhonie bez kabla, z linku otwartego w Safari. Kolejny build pojawi się na liście aplikacji. Po wejściu w aplikację wybierzesz także konkretną wcześniejszą wersję.

Potrzebujesz aktywnego Apple Developer Program, uprawnień do zarządzania certyfikatami, identyfikatorami i profilami, repozytorium aplikacji oraz iPhone’a. Kompilację i podpisywanie wykona macOS w GitHub Actions. Minuty CI podlegają limitom i rozliczeniom Twojego konta.

Ta część opisuje centralne podpisywanie w Vibe iOS App: repo klienta buduje artefakt, prywatne repo podpisujące eksportuje IPA, a repo strony publikuje instalator. W tutorialu 2 kompilacja i podpisywanie odbywały się w jednym repo. Nie kopiuj starych sekretów do repo klienta.

Ad Hoc wymaga App ID, ale sama dystrybucja Ad Hoc nie wymaga rekordu aplikacji w App Store Connect ani grupy TestFlight. Platforma Vibe iOS App zachowuje swój istniejący provisioning TestFlight jako domyślny.

Przykłady plików i nazwa „Testowa Apka” są poglądowe. Repozytoria feegloo/vibe-ios-app i feegloo/feegloo.github.io pokazują rzeczywistą architekturę tej platformy. Własna instalacja wymaga zmiany właściciela, domeny, konfiguracji backendu i uprawnień. Sam plik YAML nie tworzy całej platformy.

2. Najpierw sprawdź zasoby z TestFlight

Otwórz Certificates i wybierz właściwy zespół. Jeśli masz ważny Apple Distribution oraz odpowiadający mu klucz prywatny, wykorzystaj je ponownie. Nie twórz nowego certyfikatu tylko dla kolejnego sposobu instalacji.

Na Macu sprawdź Dostęp do pęku kluczy → Logowanie → Moje certyfikaty. Po rozwinięciu Apple Distribution powinien być widoczny klucz prywatny. Jeśli zachowałeś gotowy AppleDistribution.p12 i znasz jego hasło, możesz użyć tego pliku. Jeżeli centralny TestFlight działa z poprawnymi sekretami, nie trzeba wgrywać ich ponownie.

Sam .cer nie zawiera klucza prywatnego. Najpierw poszukaj oryginalnego Maca lub kopii .p12. Nie unieważniaj działającego certyfikatu TestFlight. Certyfikat Apple Development z części o kablu nie zastępuje Apple Distribution w tym workflow.

Masz poprawny komplet? Pomiń tworzenie CSR i certyfikatu. Przejdź do sprawdzenia sekretów. Profil App Store pozostaje dla TestFlight; profil Ad Hoc przygotujemy osobno.

3. Nie masz certyfikatu? Przygotuj CSR i .p12

Ten krok wykonaj tylko, jeśli nie masz poprawnego kompletu z kroku 2. Nie nadpisuj istniejących kluczy.

Wykonaj tylko jedną zakładkę. Każda prowadzi od CSR do gotowego AppleDistribution.p12. Potem przejdź do kroku 4 tego tutorialu. Podstawą są dokumentacja CSR oraz dokumentacja PKCS#12.

macOS: CSR w Dostępie do pęku kluczy

  1. Otwórz Dostęp do pęku kluczy / Keychain Access przez Spotlight. Wybierz pęk Logowanie.
  2. W menu aplikacji wybierz Asystent certyfikatów → Poproś o certyfikat z urzędu certyfikacji (Certificate Assistant → Request a Certificate From a Certificate Authority).
  3. Wpisz swój e-mail i nazwę rozpoznawczą, np. Jan Kowalski Distribution. Pole e-mail urzędu certyfikacji pozostaw puste. Zaznacz Zapisany na dysku / Saved to disk.
  4. Kliknij Dalej i zapisz CSR, np. na Biurku. Jeżeli pojawi się wybór parametrów klucza, użyj RSA 2048 bitów.

Wystawienie certyfikatu przez Apple

  1. Otwórz Apple Developer → Certificates i wybierz właściwy zespół.
  2. Kliknij +, zaznacz Apple Distribution i kliknij Continue.
  3. Wybierz Choose File i wskaż utworzony plik CSR. Wyślij go przez Continue.
  4. Kliknij Download. Zapisz distribution.cer w katalogu z kluczem/CSR.

Do Apple przesyłasz CSR. Prywatny klucz zostaje u Ciebie. Instrukcja CSR Apple.

Import i eksport .p12

  1. Otwórz pobrany distribution.cer dwuklikiem na tym samym Macu, na którym powstał CSR.
  2. W Logowanie → Moje certyfikaty wyszukaj Apple Distribution. Rozwiń strzałkę przy certyfikacie. Pod nim musi być klucz prywatny.
  3. Zaznacz certyfikat z powiązanym kluczem, wybierz eksport z menu kontekstowego lub Plik → Eksportuj rzeczy.
  4. Wybierz format Wymiana danych osobistych (.p12), nazwę AppleDistribution.p12 i zapisz na Biurku.
  5. Ustaw hasło eksportu, powtórz je i zachowaj. Jeżeli macOS poprosi dodatkowo o hasło pęku kluczy, jest to osobne potwierdzenie systemowe.

Jeżeli .p12 nie jest dostępny, sprawdź, czy eksportujesz także pasujący klucz prywatny. Import samego .cer na innym komputerze nie odtworzy klucza.

Pozostaw domyślne ustawienia zaufania. W razie błędu sprawdź ważność certyfikatu i łańcuch Apple WWDR. Nie omijaj błędu przez „Zawsze ufaj”.
Ścieżka Windows została opisana na podstawie dokumentacji OpenSSL. Nie wykonywaliśmy jej na Windowsie podczas tego tutorialu. Podpisywanie nowego kanału Ad Hoc sprawdzimy po konfiguracji i pierwszej instalacji.

Windows: przygotuj OpenSSL

Zainstaluj Git for Windows z oficjalnej strony i otwórz Git Bash. Poniższe komendy wpisuj w Git Bash, nie w PowerShell. Sprawdź dostępność:

openssl version

Jeżeli polecenie nie jest znalezione, sprawdź instalację Git Bash lub zainstaluj dystrybucję OpenSSL wskazaną na liście OpenSSL. Nie pobieraj kluczy ani gotowego .p12 z internetu.

mkdir -p ~/adhoc-signing
cd ~/adhoc-signing
export MSYS_NO_PATHCONV=1

Ostatnia linia zapobiega zamianie parametru /CN=... na ścieżkę Windows przez Git Bash. Folder znajduje się zwykle w C:\Users\TwojLogin\adhoc-signing; pwd -W pokaże jego dokładną ścieżkę.

openssl genpkey -algorithm RSA -aes-256-cbc -pkeyopt rsa_keygen_bits:2048 -out distribution.key
openssl req -new -sha256 -key distribution.key -out distribution.csr -subj "/CN=Jan Kowalski Distribution/emailAddress=jan@example.com"

Pierwsza komenda pyta o hasło chroniące klucz prywatny, druga o to samo hasło. W polach CN oraz emailAddress wpisz własne dane. Nie nadpisuj istniejącego klucza, dla którego wystawiono już certyfikat.

Wystawienie certyfikatu przez Apple

  1. Otwórz Apple Developer → Certificates i wybierz właściwy zespół.
  2. Kliknij +, zaznacz Apple Distribution i kliknij Continue.
  3. Wybierz Choose File i wskaż utworzony plik CSR. Wyślij go przez Continue.
  4. Kliknij Download. Zapisz distribution.cer w katalogu z kluczem/CSR.

Do Apple przesyłasz CSR. Prywatny klucz zostaje u Ciebie. Instrukcja CSR Apple.

openssl x509 -inform DER -in distribution.cer -out distribution.pem
openssl pkcs12 -export -inkey distribution.key -in distribution.pem -name "Apple Distribution" -out AppleDistribution.p12

Przy eksporcie podaj hasło prywatnego klucza, a następnie nowe hasło eksportu .p12 (Export Password). To drugie trafi do DISTRIBUTION_CERTIFICATE_PASSWORD. Certyfikat .cer musi pochodzić z CSR utworzonego z tego klucza.

Sprawdź zawartość bez wypisywania klucza:

openssl pkcs12 -info -noout -in AppleDistribution.p12

Wynik powinien zawierać certyfikat oraz zaszyfrowany klucz, np. Certificate bag i Shrouded Keybag. Błąd niezgodności klucza i certyfikatu oznacza, że używasz innej pary plików.

4. Dodaj certyfikat do centralnych Secrets

Otwórz repo podpisujące Vibe iOS App → Settings → Secrets and variables → Actions → Secrets. W tej konfiguracji jest to feegloo/vibe-ios-app. Sekretów Apple nie zapisujemy w repozytoriach aplikacji.

Na Macu skopiuj Base64 pliku .p12 do schowka:

base64 -i ~/Desktop/AppleDistribution.p12 | tr -d '\n' | pbcopy

Jeśli plik leży gdzie indziej, popraw ścieżkę. Nic nie musi pojawić się w Terminalu. Kliknij New repository secret i dodaj:

NameSecret
DISTRIBUTION_CERTIFICATE_P12_BASE64Cała zawartość schowka.
DISTRIBUTION_CERTIFICATE_PASSWORDHasło eksportu .p12, bez Base64.

Po każdym wpisie kliknij Add secret. Jeśli te sekrety już działają dla TestFlight, pozostaw je. GitHub nie pokaże później ich wartości; brak podglądu nie oznacza, że sekret jest pusty.

Windows i Linux: przygotowanie wartości sekretu

PowerShell na Windows:

[Convert]::ToBase64String([IO.File]::ReadAllBytes("$HOME\adhoc-signing\AppleDistribution.p12")) | Set-Clipboard

Linux, w katalogu z plikiem:

umask 077
base64 -w 0 AppleDistribution.p12 > AppleDistribution.p12.base64.txt

Otwórz plik tekstowy i skopiuj całość do sekretu. Base64 to kodowanie, nie szyfrowanie. Nie dodawaj żadnego z tych plików do Git.

5. Sprawdź App ID i Team ID

Otwórz Identifiers. Wybierz App ID swojej aplikacji i porównaj Bundle ID z projektem. Dla nowej aplikacji z formularza Vibe iOS App identyfikator przygotowuje backend.

Jeśli zaczynasz od zera, wykonaj rejestrację z części 1: + → App IDs → App → Explicit → własny Bundle ID → Continue → Register. Nie twórz drugiego identyfikatora dla tej samej aplikacji.

W koncie Apple Developer sprawdź Team ID. W centralnym repo otwórz Actions → Variables → New repository variable i zapisz go jako APPLE_TEAM_ID. To 10 znaków; nie jest to Issuer ID.

6. Odczytaj UDID i zarejestruj iPhone’a

Jeśli iPhone jest już aktywny na liście Devices, sprawdź jego UDID i pomiń rejestrację.

UDID odczytasz przez stronę z profilem Device UDID albo z Findera po podłączeniu telefonu. W Finderze klikaj wiersz informacji pod nazwą iPhone’a, aż zobaczysz UDID. Nie kopiuj EID. Szczegółową ścieżkę z Finderem pokazuje tutorial 3.

Profil odczytujący UDID to nie profil Ad Hoc. Samo jego zainstalowanie nie dodaje telefonu do konta Apple Developer ani do podpisu aplikacji. Integrację automatycznej rejestracji ze stroną UDID zostawiamy na później.

  1. Devices → + → Register a Device.
  2. Wybierz platformę iOS, wpisz rozpoznawalną Device Name i własny Device ID (UDID).
  3. Kliknij Continue i porównaj dane.
  4. Kliknij Register. Sprawdź, czy urządzenie jest aktywne.

Nie wyłączaj istniejącego urządzenia, aby odtworzyć tutorial. Apple stosuje limit rejestracji urządzeń; wyłączenie urządzenia w trakcie roku nie przywraca wykorzystanego miejsca.

7. Sprawdź klucz API Apple

Nowy signer automatycznie dobiera profil Ad Hoc. Do tego używa Team API key, który może zarządzać provisioningiem. Sam klucz o uprawnieniach wystarczających do uploadu w tutorialu 2 może nie wystarczyć.

Najpierw sprawdź istniejący klucz używany przez centralny TestFlight. Jeśli ma odpowiedni dostęp i zachowany plik .p8, wykorzystaj go ponownie.

  1. App Store Connect → Users and Access → Integrations → App Store Connect API → Team Keys.
  2. Gdy potrzebujesz nowego klucza, wybierz Generate API Key, nadaj nazwę, np. Vibe iOS Signing, i rolę Admin. Pierwsze użycie API może wymagać włączenia przez Account Holder.
  3. Pobierz AuthKey_TWOJ_KEY_ID.p8. Można go pobrać tylko raz.
  4. Zapisz Key ID i Issuer ID z tego samego zespołu.
Typ w centralnym GitHubNazwaWartość
VariableASC_KEY_IDKey ID.
VariableASC_ISSUER_IDIssuer ID.
SecretASC_PRIVATE_KEYCały .p8 jako tekst PEM, bez Base64.

Mac, po podmianie nazwy pliku:

pbcopy < ~/Desktop/AuthKey_TWOJ_KEY_ID.p8

Na innych systemach otwórz .p8 w edytorze i skopiuj całość, łącznie z liniami BEGIN PRIVATE KEY i END PRIVATE KEY.

To konfiguracja współdzielona z centralnym TestFlight. Nie zmieniaj tylko jednego z trzech elementów. Jeśli wymieniasz klucz również w backendzie, zachowaj zgodność tych samych trzech wartości w Supabase Secrets. Nowy kanał używa API do profili, ale nie wysyła IPA do TestFlight.

8. Profil Ad Hoc: co zrobi signer

Profil łączy konkretny Bundle ID, certyfikat i listę urządzeń. Profil App Store z części 2 zostaje dla TestFlight. Profil Development z części 3 też nie pasuje do tego eksportu.

Signer najpierw szuka aktywnego profilu IOS_APP_ADHOC, zgodnego z certyfikatem w .p12, zespołem i dokładną listą aktywnych urządzeń iOS. Jeśli profil jest ważny dłużej niż dobę, używa go ponownie. Jeśli nie ma odpowiedniego, tworzy nowy. Nie tworzy nowych certyfikatów.

W pierwszej wersji obejmujemy wszystkie aktywne urządzenia platformy iOS w tym zespole. Nie ma jeszcze oddzielnej listy urządzeń dla każdego klienta.

Chcesz przejść przez portal i przygotować pierwszy profil ręcznie?
  1. Otwórz Profiles, kliknij + i wybierz Distribution → Ad Hoc → Continue.
  2. Wybierz App ID zgodny z projektem.
  3. Zaznacz Apple Distribution odpowiadający centralnemu .p12.
  4. Zaznacz aktywne urządzenia iOS używane przez signer.
  5. Nadaj nazwę, np. TestowaApka-AdHoc, wybierz Generate, następnie Download.

Jeżeli taki profil już istnieje, tylko go sprawdź. Zgodny profil utworzony ręcznie również zostanie znaleziony przez API. Nie dodajemy sekretu ADHOC_PROVISIONING_PROFILE_BASE64: centralny signer pobiera profil dla danej aplikacji.

9. GitHub App: połącz repozytoria

Jeśli centralny TestFlight już działa, wykorzystaj istniejącą GitHub App. Sprawdź uprawnienia i dodaj dostęp do repo strony. Nie twórz drugiej integracji tylko dla Ad Hoc.

  1. GitHub → Settings → Developer settings → GitHub Apps → wybierz istniejącą App. Od zera wybierz New GitHub App, nazwę i adres swojej usługi.
  2. Webhook URL ustaw na adres funkcji testflight-webhook w swoim projekcie Supabase. Dla tej platformy: https://gwfdnwlhonszocjizrnl.supabase.co/functions/v1/testflight-webhook.
  3. Ustaw losowy Webhook secret. Tę samą wartość backend przechowuje w VIBEIOSAPP_GITHUB_APP_WEBHOOK_SECRET.
  4. Repository permissions: Actions: Read and write oraz Contents: Read and write. Zachowaj Administration: Read and write potrzebne pozostałemu provisioningowi platformy.
  5. Subscribe to events: Workflow run. Zapisz zmiany i zaakceptuj rozszerzenie uprawnień istniejącej instalacji.
  6. Install App: obejmij repo aplikacji, repo podpisujące i repo strony. Tutaj są to repozytoria na koncie feegloo.
  7. W ustawieniach General sprawdź App ID i Private keys. Jeśli nie masz klucza prywatnego App, wygeneruj go i pobierz PEM.

W centralnym repo zapisz Variable VIBEIOSAPP_GITHUB_APP_ID oraz Secret VIBEIOSAPP_GITHUB_APP_PRIVATE_KEY z pełną treścią PEM. Backend w Supabase używa tych samych nazw. Nie myl App ID z Client ID i tego klucza z Apple .p8.

Workflow tworzy krótkotrwały token tylko do odczytu artefaktu źródłowego oraz osobny token Contents write do publikacji w repo strony. Nie potrzebujesz nowego PAT BUILDS_REPO_TOKEN ze starego workflow Trichology.

Pełny setup platformy, w tym provisioning nowych repozytoriów i OAuth, jest opisany w dokumentacji repo Vibe iOS App (dostęp dla osób uprawnionych). Nie zmieniaj działającego adresu OAuth podczas dodawania Ad Hoc.

10. Sprawdź workflow i publikację

W nowo tworzonym repo platforma aktywuje .github/workflows/adhoc-build.yml. W template plik ma końcówkę .disabled, aby szablon sam nie budował aplikacji.

MiejsceCo powinno być gotowe
Repo aplikacjiWorkflow Build Ad Hoc artifact i projekt Swift/XcodeGen.
Centralne repoadhoc-sign.yml oraz scripts/adhoc/profile.py i publish.py.
SupabaseWdrożone testflight-webhook i provision-app z obsługą Ad Hoc.

Źródło i instrukcja wdrożenia: docs/adhoc.md. Workflow klienta: template. Te repozytoria mogą wymagać zalogowania z uprawnieniami.

Istniejące repozytorium nie aktualizuje się automatycznie po zmianie template. Trzeba dodać do niego workflow osobno. Signer przyjmuje tylko zarejestrowane repo ID, właściwy Bundle ID i udany build z main.

W tej wersji podpisujemy jedną aplikację bez rozszerzeń i Watch. IPA musi mieć mniej niż 100 MiB, bo zapisujemy je w Git. Duże aplikacje potrzebują osobnego hostingu plików. Zwykłe artefakty Actions nie są trwałym publicznym adresem instalacji.

IPA i manifest są publicznie dostępne. iOS nadal wymaga urządzenia dopuszczonego przez profil. Podpisany IPA zawiera profil z UDID urządzeń, więc nie traktuj takiego hostingu jako prywatnego magazynu.

11. Uruchom Ad Hoc bez TestFlight

Najprościej: repo aplikacji → Actions → Build Ad Hoc artifact → Run workflow → main → Run workflow. Ręczne uruchomienie tego workflow nie uruchamia workflow TestFlight.

Jeżeli właśnie zmieniasz kod i chcesz opublikować go tylko przez Ad Hoc, dopisz do wiadomości ostatniego commita:

Add breathing animation [adhoc] [skip testflight]
UruchomienieEfekt w nowej platformie
Zwykły push na mainDomyślny TestFlight; job Ad Hoc pominięty.
[adhoc]Ad Hoc i domyślny TestFlight.
[adhoc] [skip testflight]Tylko Ad Hoc.
Run workflow: Build Ad Hoc artifactTylko ręcznie wybrany Ad Hoc.

Przy kilku commitach w jednym pushu znaczniki muszą być w ostatnim. Przy squash merge umieść je w końcowej wiadomości squasha. Nie twórz pustych commitów do uruchamiania buildu.

Workflow ma zdarzenie push w YAML, żeby odczytać znacznik, ale zwykły push nie wykonuje joba kompilującego Ad Hoc. W Actions może pojawić się wpis skipped. Reguły te dotyczą nowej platformy, nie zmieniają historycznych workflow z tutoriali 2 i 3.

12. Sprawdź centralne podpisanie

Po zakończeniu builda klienta pojawi się artefakt unsigned-ios-adhoc-archive. GitHub App przekaże zdarzenie do backendu, a ten uruchomi Sign and publish Ad Hoc artifact w centralnym repo.

Signer zweryfikuje źródło, pobierze archiwum, przygotuje profil, podpisze IPA i zapisze nową wersję w repo strony. Po publikacji GitHub Pages pojawi się ona na stronie Ad Hoc. Zielony workflow źródłowy potwierdza tylko build; nie zastępuje sprawdzenia podpisywania i publikacji.

Nie ma etapu Processing w TestFlight. Są natomiast osobne etapy kompilacji, podpisywania i publikacji strony. Nie uruchamiaj kolejnych buildów tylko dlatego, że Pages jeszcze publikuje.

Artefakt niepodpisany ma retencję 1 dzień. Jeśli wygasł, uruchom ponownie workflow klienta. Numer buildu pochodzi z GITHUB_RUN_NUMBER klienta; Re-run tego samego runa zachowuje numer.

13. Zainstaluj aplikację z Safari

  1. Na zarejestrowanym iPhonie otwórz aleksanderfigiel.pl/adhoc/ w Safari.
  2. Znajdź ikonę, nazwę i wersję aplikacji.
  3. Naciśnij Install i potwierdź instalację w komunikacie iOS.
  4. Poczekaj na zakończenie instalacji na ekranie początkowym i otwórz aplikację.

Strona wywołuje link itms-services do manifestu HTTPS, który wskazuje podpisany plik IPA. Nie musisz ręcznie pobierać i otwierać IPA z aplikacji Pliki.

Jeśli masz tę samą aplikację z TestFlight, przejście pomiędzy kanałami może wymagać usunięcia poprzedniej instalacji. Najpierw zabezpiecz lokalne dane. Nie traktuj usuwania aplikacji jako obowiązkowego kroku każdej aktualizacji.

14. Aktualizacja i wybór konkretnej wersji

Po kolejnej zmianie uruchom nowy build Ad Hoc. Na liście zobaczysz najnowszą opublikowaną wersję. Naciśnij Install, żeby ją wgrać. Przy tym samym Bundle ID i zgodnym podpisie nowa instalacja Ad Hoc może aktualizować poprzednią.

Tapnij nazwę lub ikonę aplikacji, aby otworzyć historię. Przy każdej wersji jest osobny Install. Starszy build nadal musi mieć ważny podpis i obejmować Twój telefon w swoim profilu. Cofnięcie wersji może być niezgodne z danymi zapisanymi przez nowszą aplikację.

Przycisk nie zmienia się automatycznie na Update ani Open. Safari nie udostępnia stronie wiarygodnej informacji o zainstalowanej wersji, a samo kliknięcie Install nie potwierdza sukcesu.

Po dodaniu nowego iPhone’a do Apple Developer uruchom nowe podpisywanie. Nowy profil obejmie urządzenie; stare IPA pozostaną ze starą listą. Ważność Ad Hoc zależy od podpisu i profilu, nie od 90 dni TestFlight.
