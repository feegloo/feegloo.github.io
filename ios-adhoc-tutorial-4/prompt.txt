Otwórz i przeczytaj tutorial 4 przed rozpoczęciem. Jeśli nie masz dostępu, poproś o treść; nie udawaj odczytu. Poprowadź mnie po polsku przez centralne podpisywanie i instalację Ad Hoc, po jednym małym kroku na wiadomość. Po każdym kroku czekaj na moje potwierdzenie lub screenshot. Nie wyświetlaj od razu całej instrukcji.
Najpierw ustal, czy konfigurujemy istniejące Vibe iOS App, czy własną instalację, i jaki mam system. Sprawdź konto Apple Developer i rzeczywiste uprawnienia. Nie przypisuj mi identyfikatorów z przykładów. W nowej instalacji sam plik workflow nie zastępuje backendu i rejestracji repo.
Zacznij od istniejących zasobów TestFlight. Użyj ponownie ważnego Apple Distribution wraz z kluczem prywatnym i .p12, jeśli jest dostępny. Nie twórz duplikatów dla screenów. Nie unieważniaj certyfikatów. Sam .cer nie wystarczy. Apple Development nie zastępuje Apple Distribution. Jeśli zasobów brakuje, przejdź przez CSR, portal Certificates, pobranie .cer i eksport .p12. Nie proś o hasła, klucze prywatne, pliki .p12, .p8 ani wartości sekretów w czacie.
Sekrety Apple należą tylko do centralnego repo. DISTRIBUTION_CERTIFICATE_P12_BASE64 to Base64 .p12, DISTRIBUTION_CERTIFICATE_PASSWORD to surowe hasło eksportu. ASC_PRIVATE_KEY to pełny PEM .p8 bez Base64. APPLE_TEAM_ID, ASC_KEY_ID, ASC_ISSUER_ID i VIBEIOSAPP_GITHUB_APP_ID to Variables. GitHub App private PEM to VIBEIOSAPP_GITHUB_APP_PRIVATE_KEY. Nie nadpisuj działających sekretów tylko w ramach powtórzenia tutorialu.
Sprawdź istniejący App ID, zgodność Bundle ID i zespół. Sprawdź, czy iPhone jest zarejestrowany w Apple Devices. Odczyt UDID przez profil nie rejestruje urządzenia. Nie myl UDID z EID. Nie wyłączaj istniejących urządzeń.
Sprawdź Team API key Apple. Nowy setup używa Admin do provisioning API. Klucz Developer z historycznego uploadu może nie wystarczyć. Użyj istniejącego odpowiedniego klucza, jeśli jest. Zmiany klucza współdzielonego z TestFlight wymagają zgodnych ID i .p8, także w Supabase, jeśli go tam wymieniamy.
Profil Ad Hoc jest osobny od App Store i Development. Signer używa zgodnego istniejącego profilu albo tworzy go przez API dla wszystkich aktywnych urządzeń iOS zespołu. Ręczne przejście po ekranach Profiles jest opcjonalne i nie wymaga tworzenia duplikatu. Nie dodawaj sekretu ADHOC_PROVISIONING_PROFILE_BASE64 do nowego rozwiązania.
Sprawdź GitHub App: Actions write, Contents write, Workflow run, dostęp do repo klienta, signera i strony oraz zaakceptowane uprawnienia instalacji. Zachowaj dotychczasowy webhook i OAuth działającej platformy. Dopiero przy brakującym elemencie podaj dokładne kroki jego utworzenia.
TestFlight jest domyślny. Tylko Ad Hoc: [adhoc] [skip testflight] w ostatnim commicie pusha albo manualny Build Ad Hoc artifact na main. Nie twórz pustych commitów. Zwykły push pomija job Ad Hoc. Po buildzie sprawdź osobno signer i Pages. Nie deklaruj udanego eksportu lub instalacji bez dowodów.
Prowadź przez Safari, Install, otwarcie aplikacji, kolejną wersję i historię. Strona nie wykrywa instalacji i nie udaje Update/Open. Nie obiecuj zachowania danych przy zmianie kanału ani downgradowaniu. Zabezpiecz dane przed ewentualnym usuwaniem aplikacji. Nowe urządzenie wymaga nowego podpisanego IPA.
Przyjmuj screenshoty po jednym i dopasowuj instrukcję do rzeczywistego ekranu. Przed publikacją anonimizuj dane, bez kluczy i sekretów. Nie używaj znaku em dash. Zakończ zestawieniem potwierdzonych kroków i braków. Nie publikuj w App Store.
